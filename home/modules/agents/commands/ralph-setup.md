# Ralph Loop Setup Wizard

ユーザーと対話しながら、最適な ralph-loop の呼び出しを組み立てる。

## 入力の確認

$ARGUMENTS が指定されている場合、それをタスクの初期情報として扱う。

## ヒアリング手順

以下のステップを対話的に進める。一度に全部聞かず、ステップごとにユーザーと会話すること。

### Step 1: タスクの把握

ユーザーにタスクの目的をヒアリングする。以下を明確にする:

- 何を達成したいのか
- 対象のファイル・ディレクトリ
- 技術的な制約や前提条件

必要に応じてコードベースを読んで文脈を理解する。

### Step 2: 完了条件の定義

`--completion-promise` に設定する文言を一緒に決める。

良い完了条件の基準:
- **客観的に検証可能** であること（例: "All tests passing", "No TypeScript errors", "Build succeeds"）
- **曖昧でない** こと（"コードが改善された" はダメ）
- **Claude が自力で判定できる** こと（コマンド実行で確認できるのが理想）

ユーザーの意図に基づいて具体的な文言を提案し、合意を取る。

### Step 3: 反復回数の決定

`--max-iterations` を決める。目安を提示する:

- 小規模（バグ修正、小さなリファクタ）: 5-10
- 中規模（機能追加、テスト整備）: 10-20
- 大規模（大きなリファクタ、複数ファイルの変更）: 20-50

無制限（0）は推奨しない。理由も説明する。

### Step 4: プロンプトの構成

ここまでの情報をもとに、ralph-loop に渡すプロンプトを組み立てる。

良いプロンプトの構成:
1. タスクの明確な説明（何を、なぜ）
2. 対象の範囲（どのファイル・ディレクトリ）
3. 各イテレーションで行うべきアクション
4. 成功の判定方法（どのコマンドで確認するか）

### Step 5: 確認と実行

組み立てたプロンプト・完了条件・反復回数をユーザーに提示し、確認を得る。

**重要: ralph-loop の呼び出し手順**

長いプロンプト（特に日本語マルチライン）を Skill tool の引数として直接渡すと、シェルのフラグ解析に失敗する。必ず以下の手順で実行すること:

1. プロンプト全文を `.claude/ralph-prompt-{task-id}.local.md` に書き出す
2. ralph-loop の状態ファイル `.claude/ralph-loop.local.md` を直接作成する:

```markdown
---
active: true
iteration: 1
max_iterations: [N]
completion_promise: "[条件]"
started_at: "[ISO 8601 タイムスタンプ]"
---

[.claude/ralph-prompt-{task-id}.local.md の内容をここに展開]
```

3. 状態ファイルを作成したら、プロンプトの内容に従って作業を開始する

## エビデンス保存規約

ralph-loop 内で行った検証の結果は、`/ralph-pr` で PR 用 markdown を生成する際の入力となる。以下の規約に従って保存すること。

**保存先:** `agent_docs/{issue-id}/`

```
agent_docs/{issue-id}/
  screenshots/          ← スクリーンショット（UI 検証時）
    01-before.png
    02-after.png
  logs/                 ← ブラウザ・サーバーログの抜粋
    browser-console.txt
    server-error.txt
  verification-report.local.md  ← 検証結果サマリー
```

**プロンプトに必ず含めること:**

- 検証で得たエビデンス（スクショ、ログ、テスト結果等）を上記ディレクトリに保存する指示
- `verification-report.local.md` に検証結果のサマリーを書く指示
- このサマリーには「何を検証し、結果がどうだったか」を簡潔にまとめる

## 重要な注意事項

- completion-promise は Claude が嘘をつけない仕組み。真に検証可能な条件のみ設定すること
- プロンプトが具体的であるほどループは早く収束する
- 曖昧な指示は無駄なイテレーションの原因になる
