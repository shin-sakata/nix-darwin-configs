# Ralph Pre-Setup: 検証手段確立ウィザード

ralph-setup の前段階。曖昧な issue に対して「そもそもどうやって検証するのか」すら分からない状態から、ralph-loop を使って実際に手を動かしながら検証手段を確立し、実装可能なタスク定義にまで落とし込む。

## 目的

「検証手段すら存在しない」状態から、以下を確立すること:

1. 問題の再現方法（どの画面で、どの操作をすると、何が起きるか）
2. 検証手段（どうやって「直った」と判断するか）
3. テストデータの準備手順（検証に必要な状態をどう作るか）
4. 上記を踏まえた実装タスクの分解

## 入力の確認

$ARGUMENTS が指定されている場合、それを issue の参照情報（URL や概要）として扱う。

## ヒアリング手順

以下のステップを対話的に進める。一度に全部聞かず、ステップごとにユーザーと会話すること。

### Step 1: Issue の取得と現状把握

ユーザーから issue の参照情報を受け取る:

- Notion URL → MCP で取得
- GitHub issue URL → `gh` コマンドで取得
- テキスト → そのまま利用

issue の内容を読み込んだ上で、以下を整理してユーザーに提示する:

- issue の要約（自分の言葉で）
- 不明点・曖昧な箇所のリスト
- 親 issue やサブアイテムがあれば、その関係性

さらに、**現時点で検証手段として何が欠けているか** を明示する:

- 問題を再現する手順が分かっているか？
- 再現に必要なデータやアカウントはあるか？
- どの画面・API を見れば問題を確認できるか分かっているか？
- 「修正完了」の判定基準はあるか？

### Step 2: 検証環境の確認

検証を行うために必要な情報をヒアリングする:

- **対象リポジトリ**: パス、ブランチ
- **ローカル開発環境**: 起動方法、URL（例: `localhost:3000`）
- **利用可能なツール**: Playwright MCP が使えるか、ブラウザは何か
- **テストアカウント**: ログインに必要な認証情報の場所
- **テストデータ**: 既存のものがあるか、作る必要があるか
- **外部依存**: 他のサービスやモックが必要か

### Step 3: 調査の優先順位

何を先に調べるべきかユーザーと合意する。典型的な順序:

1. **コード調査**: 関連コードを読んで問題の根本原因を特定
2. **データ準備**: 検証に必要な状態を作る手順を確立
3. **再現確認**: Playwright MCP 等で実際に問題を再現
4. **修正方針の策定**: どこをどう変えれば直るかの仮説
5. **検証手順の確定**: 修正後に「直った」と判断する手順

ユーザーの状況に応じて順序を調整する。

### Step 4: Ralph Loop の組み立て

ここまでの情報をもとに、**検証手段確立のための** ralph-loop を組み立てる。

**このループの特徴:**

- 実装は行わない。調査とドキュメント作成のみ
- 各イテレーションで実際にコードを読み、UI を触り、データを作り、検証手段を試行錯誤する
- 結果を `agent_docs/{issue-id}-task-breakdown.md` にまとめる

**完了条件の設計基準:**

出力ファイルが存在し、以下を全て含むこと:
- 問題の再現手順（具体的な操作ステップ）
- テストデータの準備手順（必要なデータの作り方）
- Playwright MCP / 手動での検証手順（URL・操作・期待結果）
- 実装タスク一覧（対象ファイルパス・変更内容）

**プロンプトに含めるべき要素:**

1. issue の内容と文脈
2. 検証環境の情報（リポジトリパス、URL、認証情報の場所）
3. 「まず再現手順を確立し、次にテストデータを準備し、検証手順を確定させ、最後にタスク分解をまとめる」という段階的な指示
4. Playwright MCP の使い方の具体的な指示（ある場合）
5. 出力ドキュメントの構成と要件

**反復回数の目安:**

- UI 確認不要（API/バックエンドのみ）: 5-10
- UI 確認あり（Playwright MCP 使用）: 10-20
- 複数サービス横断 + データ準備が複雑: 15-25

### Step 5: 確認と実行

組み立てたプロンプト・完了条件・反復回数をユーザーに提示し、確認を得る。

**重要: ralph-loop の呼び出し手順**

長いプロンプト（特に日本語マルチライン）を Skill tool の引数として直接渡すと、シェルのフラグ解析に失敗する。必ず以下の手順で実行すること:

1. プロンプト全文を `.claude/ralph-prompt-{issue-id}.local.md` に書き出す
2. ralph-loop の状態ファイル `.claude/ralph-loop.local.md` を直接作成する:

```markdown
---
active: true
iteration: 1
max_iterations: [N]
completion_promise: "[条件]"
started_at: "[ISO 8601 タイムスタンプ]"
---

[.claude/ralph-prompt-{issue-id}.local.md の内容をここに展開]
```

3. 状態ファイルを作成したら、プロンプトの内容に従って作業を開始する

## ralph-setup / ralph-pre-setup の関係

```
曖昧な issue
    │
    ▼
/ralph-pre-setup  ← 検証手段の確立・タスク明瞭化
    │
    ▼
タスク分解ドキュメント (agent_docs/*.md)
    │
    ▼
/ralph-setup      ← 明確なタスクに対する実装ループの構築
    │
    ▼
/ralph-loop       ← 実装の実行
```

## エビデンス収集による明瞭化

検証手段は issue の性質に応じて選択する。テストコードの実行や API を直接叩くだけで十分な場合はそれでよい。

**ただし、UI が関わる場合は以下の網羅的なエビデンス収集を必須とする。** UI 操作は曖昧になりやすく、「どの画面のどこを操作して何が起きるか」を言葉だけで伝えるのは困難なため。

### スクリーンショット（UI が関わる場合は必須）

Playwright MCP で UI を操作する際は、**必ずスクリーンショットを撮影**:

1. **操作前**: 対象画面の初期状態
2. **操作対象の特定**: クリック・入力すべき要素の位置
3. **操作後**: 期待される結果の状態
4. **エラー状態**: 問題が再現された場合の状態

スクリーンショットは `agent_docs/screenshots/{issue-id}/` に保存し、出力ドキュメントから相対パスで参照する。

### ブラウザログ（UI が関わる場合は必須）

Playwright MCP の console イベント取得や、ブラウザの DevTools コンソールを確認:

- JavaScript エラー・警告
- ネットワークリクエストの失敗（4xx / 5xx）
- リクエスト/レスポンスの内容（問題の特定に関連するもの）

### Dev Server / バックエンドログ（UI が関わる場合は必須）

ローカル開発サーバーやバックエンドのターミナル出力を確認:

- サーバーサイドの例外・スタックトレース
- SQL クエリのエラー
- 認証・認可の失敗ログ

### その他の情報源

状況に応じて以下も収集:

- **API レスポンス**: `curl` や Playwright でのリクエスト結果
- **DB の状態**: 検証に関連するレコードの状態
- **環境変数・設定値**: 動作に影響する設定

### ドキュメントへの記載方法

収集したエビデンスは、検証手順と対応させてドキュメントに含める:

```markdown
### 手順 1: モーダルを開く

![初期状態](screenshots/{issue-id}/01-initial.png)

1. 詳細画面で対象セクションを確認
2. 「...」メニューをクリック → 「削除」を選択

![エラー状態](screenshots/{issue-id}/02-error.png)

**ブラウザコンソール:**
\`\`\`
GET /api/v1/xxx/yyy 500 (Internal Server Error)
Uncaught (in promise) Error: Request failed with status code 500
\`\`\`

**サーバーログ:**
\`\`\`
ERROR: TeamAvailabilitySharingNotFoundError: sharing not found for id=xxx
    at getConfirmedEventByTeamAvailabilitySharings.ts:42
\`\`\`

→ 根本原因: GET API がリンク取得失敗時に例外をスローしている
```

これにより、ralph-setup で実装ループを組む際にも、検証者が手動で確認する際にも、「何が起きていて、どこを見ればよいか」が一目で分かる。

## 重要な注意事項

- このコマンドが生成する ralph-loop は **調査と検証手段の確立** が目的。コードの実装変更は行わない
- 検証手段はテスト実行や API 呼び出しで十分な場合はそれでよい
- **UI が関わる場合は** スクリーンショット・ブラウザログ・サーバーログを網羅的に収集すること
- **エビデンスなき記述は禁止** — 「〜のはず」ではなく、実際に確認した結果をドキュメントに含める
- テストデータの準備は、検証に必要最小限のものだけ作る方針で
- 調査の過程で issue の前提が間違っていることが分かった場合は、その旨をエビデンスとともに明記する
- Playwright MCP が使えない環境では、コードリーディングとAPI呼び出しで補完する
- 出力ドキュメントは人間が読んで判断するためのもの。過度に冗長にせず、実用的な粒度を保つ
